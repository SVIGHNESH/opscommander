OpsCommander

An AI-powered system where seven specialised agents collaborate to detect, diagnose, recommend, gate, remediate, and report on cloud and DevOps incidents — with a human-in-the-loop safety gate before any risky action.

Domain · Cloud Ops & Incident Response Difficulty · Very High LLM · Amazon Bedrock (Claude) Stack · Python · FastAPI · Streamlit · boto3
Runs offline out of the box. Every AWS integration — Bedrock, CloudWatch, DynamoDB, S3, SNS — ships with a local mock. python scripts/seed_incident.py works with zero configuration and zero cloud credentials. Set OPSCOMMANDER_MODE=aws to switch to real services.

Instead of a single monolithic agent, OpsCommander decomposes incident response into a pipeline of focused agents. A single Incident object threads through all of them: each agent reads what it needs and writes its structured result back, so by the time the Reporting Agent runs, the object is the complete audit record.

AWS services used

Amazon Bedrock CloudWatch (Logs + Metrics) DynamoDB Amazon S3 Amazon SNS Lambda / EC2 / ECS / ASG EventBridge

Architecture

A CloudWatch alarm (or a POST /incident call) enters the pipeline. Five agents run in sequence to diagnose and decide; the Approval Agent is a gate. Safe actions within the severity ceiling proceed straight to remediation; risky, destructive, or high-severity actions halt and wait for a human. Either way, the Reporting Agent produces the artifacts.

The design has two structural properties worth calling out:

  • One object, seven agents. Sequencing lives in the orchestrator; each agent owns exactly one concern and communicates only through the shared Incident.
  • Graceful degradation everywhere. Missing boto3, absent credentials, or a failed Bedrock call fall back to deterministic local behaviour rather than crashing the run.

Workflow

The incident state machine:

Detected → Analyzing → (Recommendation) → Approval
                                              ├─ auto-approved ──▶ Remediating ──▶ Resolved / Failed
                                              └─ escalated ──────▶ AwaitingApproval
                                                                        │  POST /approve
                                                                        ▼
                                                                   Remediating ──▶ Resolved

Every stage transition and agent action appends a timestamped entry to the incident timeline, and the incident is persisted after each agent, so it is inspectable mid-flight and recoverable if a stage fails.

The Seven Agents

1

Detection

Normalises the incoming alarm into a titled, severity-scored incident and pulls the initial metric snapshot. Can raise a caller-supplied severity but never lowers it.

CloudWatch Metrics
2

Log Analysis

Reads recent logs, extracts exceptions/errors, and infers a likely root cause with explainable, ordered pattern rules.

CloudWatch Logs
3

Infrastructure

Reviews the health of the resources behind the service so later agents reason about current state, not the alarm alone.

Lambda · EC2 · APIGW · ECS
4

Recommendation

Sends the incident context to Amazon Bedrock (Claude) and gets back prioritised, machine-actionable fixes. Deterministic rule engine when Bedrock is unavailable.

Amazon Bedrock
5

Approval

The safety gate. Classifies the top action's risk and decides auto-approve vs. escalate. Destructive actions always require a human.

policy engine
6

Remediation

Executes the approved action — and only an approved one — through the infrastructure adapter.

Lambda · ASG · ECS
7

Reporting

Compiles the report (JSON, Markdown, PDF), persists it to S3/local, and fires SNS + Slack notifications.

S3 · SNS · Slack

Approval & Safety

The Approval Agent classifies every proposed action into one of three risk tiers. Only safe actions can ever be auto-executed, and only when the incident severity is at or below the configured ceiling (OPSCOMMANDER_AUTO_APPROVE_SEVERITY, default High).

RiskExample actionsBehaviour
safe restart_lambda, increase_lambda_timeout, increase_db_connections, clear_failed_jobs Auto-approved if severity ≤ ceiling; otherwise escalated.
risky scale_asg, trigger_deployment, rotate_credentials, unknown actions Always escalated to a human.
destructive delete_database, terminate_ec2, drop_table Never auto-executed — hard-blocked pending explicit human approval.
The Remediation Agent will not run an unapproved action. Even if a bug elsewhere proposed a destructive fix, the two-layer guard (classification + the remediation agent's approval check) prevents automated execution.

HTTP API

FastAPI. Start with ./run.sh api and browse interactive docs at /docs.

MethodPathPurpose
POST/incidentCreate and run an incident through the pipeline
GET/incident/{id}Full incident state (agents, timeline, ...)
GET/incidentsList recent incident summaries
POST/approveApprove a halted incident's remediation
GET/report/{id}Report as ?fmt=markdown (default) or json
GET/healthzLiveness + current mode

Create an incident

curl -X POST localhost:8000/incident \
  -H 'content-type: application/json' \
  -d '{"service":"orders-api","alarm":"Database Timeout","severity":"High"}'

Sample response

{
  "id": "inc_ef059c29877b",
  "service": "orders-api",
  "severity": "High",
  "status": "Resolved",
  "root_cause": "Database connection timeout",
  "recommendation": {
    "title": "Increase database connection pool and Lambda timeout",
    "action": "increase_db_connections",
    "confidence": 0.82
  },
  "approval": {"approved": true, "auto": true, "risk": "safe"},
  "action_taken": {"action": "increase_db_connections", "executed": true, "success": true},
  "report_uri": "…/data/reports/inc_ef059c29877b.json"
}

Approve an escalated incident

curl -X POST localhost:8000/approve \
  -H 'content-type: application/json' \
  -d '{"incident_id":"inc_a275330abfd9","approved_by":"sre-oncall"}'

Data Model

The core domain models are plain dataclasses (no third-party dependencies), so the engine runs and is fully unit-tested without FastAPI, boto3, or the Anthropic SDK installed.

TypePurpose
IncidentThe object threaded through the pipeline; holds every agent result, the recommendations, approval decision, remediation outcome, and the timeline.
SeverityCritical High Medium Low Info — ordered by rank.
IncidentStatusDetected → Analyzing → AwaitingApproval → Remediating → Resolved / Escalated / Failed.
AgentResultStructured output of a single agent (ok, summary, data, timestamps).
Recommendationtitle, rationale, machine-readable action, confidence, references.
ApprovalDecisionaction, approved, auto vs. manual, reason, risk tier.
RemediationResultaction, executed, success, detail.

Configuration

Entirely environment-driven; see .env.example. Sensible defaults mean nothing is required to run locally.

VariableDefaultMeaning
OPSCOMMANDER_MODEmockmock (local fakes) or aws (real services)
AWS_REGIONus-east-1Region for Bedrock / DynamoDB / S3 / …
OPSCOMMANDER_BEDROCK_MODELanthropic.claude-opus-4-8Bedrock model id — note the anthropic. prefix Bedrock requires
OPSCOMMANDER_AUTO_APPROVE_SEVERITYHighSafe actions at/below this severity auto-approve; anything riskier escalates
OPSCOMMANDER_DDB_TABLEopscommander-incidentsDynamoDB table (aws mode)
OPSCOMMANDER_S3_BUCKETopscommander-reportsS3 bucket for reports (aws mode)
OPSCOMMANDER_SNS_TOPIC_ARNemptySNS topic for notifications
OPSCOMMANDER_SLACK_WEBHOOKemptySlack incoming-webhook URL
On Amazon Bedrock the Anthropic model id is prefixed with anthropic. (e.g. anthropic.claude-opus-4-8). The Recommendation Agent prefers the Anthropic SDK's AnthropicBedrockMantle client and falls back to raw bedrock-runtime, then to a deterministic rule engine.

Running It

# Zero-dependency demo — runs the seeded incidents through the full pipeline
python scripts/seed_incident.py

# Optional: create a venv and install the surfaces you want
python -m venv .venv && source .venv/bin/activate
pip install -e ".[all]"        # api + dashboard + aws + pdf + tests

# Convenience launcher
./run.sh demo         # seeded incidents
./run.sh test         # pytest suite
./run.sh api          # FastAPI  → http://localhost:8000  (/docs)
./run.sh dashboard    # Streamlit → http://localhost:8501

The Streamlit console lets an operator trigger incidents, watch the seven-stage pipeline light up, approve escalated remediations inline, and read the generated report.
